# Tralys.Ecs

A source-generated C# ECS (.NET 11, NativeAOT, no reflection in the core). Packages: `src/Tralys.Ecs` (core), `Tralys.Ecs.Scheduling`, `Tralys.Ecs.Executor.Pool`, `Tralys.Ecs.Testing`, and `Tralys.Ecs.Generators` (generator and analyzers).

## Build and verify

- `dotnet build Tralys.Ecs.slnx` — warnings are errors.
- `dotnet run --project tests/Tralys.Ecs.Tests --no-build`, and the same for `tests/Tralys.Ecs.Generators.Tests` and `tests/Tralys.Ecs.Scheduling.Tests`.
- `dotnet run --project tests/Tralys.Ecs.Aot.Smoke --no-build`; CI also runs `dotnet publish tests/Tralys.Ecs.Aot.Smoke -c Release` and the published binary.

## Release

- Give `CHANGELOG.md` a `## [version]` section, move every `PublicAPI.Unshipped.txt` entry into `PublicAPI.Shipped.txt` and the generator's `AnalyzerReleases.Unshipped.md` rules into a `## Release <version>` section of `AnalyzerReleases.Shipped.md`, then push `v<version>` from `master`. `release.yml` runs CI with that version, publishes to nuget.org and cuts the GitHub Release from the section; a `-` in the tag makes a prerelease.

## Rules the build enforces

- **Public API listing.** Each package has `PublicAPI.Shipped.txt`/`PublicAPI.Unshipped.txt`. A public change fails the build (RS0016/RS0017) until the list is updated: `dotnet format analyzers <csproj> --diagnostics RS0016 --severity warn`, then delete stale lines by hand.
- **Doc contracts.** Every public member in the four runtime packages needs a `///` summary (CS1591 is an error there). One line: what it does, what throws, when a write applies.
- **Effects.** Every public method of `World`, `WorldEntity`, `Lookup`, `RefLookup`, `Rows`, `Commands`, `BufferArena`, `ChangeTracking`, `WorldScratch` and `EntityBatch` carries `[Effect(...)]` (`Tralys.Ecs.Generated`), as does every public method of any other type that declares one. The flags are may-effects, and the build computes them: the closure analyzer follows each method's calls down to the primitives that mark an effect (the row-move counters, `Structural`, `CheckSettled`, `CheckSerial`, the scratch pool) and fails (TECS0047) when a declaration is missing or differs. An interface consumers implement declares its effect at the seam (TECS0048). Effects are the runtime's own: consumer code is never annotated or inferred. They prove `WorldReader` reaches nothing but reads, and they tell TECS0019 which runtime calls move storage. A borrow is a type, not a flag: a `ref` return, a ref property, or a `[Borrow]` ref struct (`Optional`, `ComponentEdit`, `RowEdit`, …), invalidated only by its own storage's moves (`MovesEntities`, `MovesRowBlocks`). Outside a walk, TECS0019 flags a borrow used after a runtime call that moves its storage, or after a method call into code that is handed or holds a world handle (a property read never counts); inside a walk nothing moves. A helper that only reads takes an `EntityReader` or `WorldReader` (`world.Reader`, `entity.Reader`), so a serial and a parallel body can share it. There are no name lists to update.
- **Must-dispose types** carry `[MustDispose("consequence")]`; TECS0032 reports an instance that is neither disposed nor handed on.

## Verb grammar

The same verbs mean the same thing on `World`, `WorldEntity`, lookups, `Rows` and generated views:

| verb | meaning |
|---|---|
| `Has` | present: stored and, for an `[Enableable]` type, enabled |
| `Get` | `ref readonly` read; throws if absent |
| `TryGet` | copy out; false if absent |
| `Find` | optional `ref readonly` read (`Optional<T>`) |
| `Edit` | scoped `ref` write; must be present; stamps and reindexes on dispose only if changed |
| `FindEdit` | as `Edit`, or an edit without a value |
| `EditOrAdd` | sets the initial value first if absent |
| `Set` | add or overwrite; enables a disabled one |
| `Replace` | overwrite; must be present |
| `Remove` | remove, enabled or disabled; false if not stored |
| `SetEnabled` | flip a stored `[Enableable]` one; `false` on a missing one does nothing, `true` throws |
| `HasStored`, `TryGetStored` | as `Has`/`TryGet`, but a disabled one counts |

A disabled `[Enableable]` component or tag is absent to every verb but the `Stored` reads, as it is to queries, indexes, views, lookups and change samples; add and remove observers see an enable as an add and a disable as a removal, and the log keeps `Enabled`/`Disabled`. An immediate write reports itself; a playback reports each component's net change over the batch, from one rule both share (`ComponentChange`). Grant with `Add<T>()` (tags) or `Set` (components), which also enable a disabled one; revoke with `SetEnabled<T>(false)`; read with `Has`/`TryGet`. Nothing needs to be born disabled.

Where two spellings exist, write the first: `TryGet` over `Find` when a copy will do; `Set` over `Add<T>()` only for components with a value (tags use `Add<T>()`).

A handle is usable while `IsLive`: it exists and neither it nor an ancestor is pending destroy. `Entity.IsDefault` only says the handle was never assigned. `World.Exists` and `WorldEntity.State` also see a pending-destroy entity, for code that reads a dying one on purpose.

`Get`, `Find` and view getters hand out readonly references. A struct method that is not `readonly`, called through one, runs on a copy and its write is lost, so TECS0046 rejects it: write through `Edit`, or mark the method `readonly` when it changes nothing.

## When writes apply

- Outside a walk, `World` writes apply at once.
- A serial `[Query]` body and a `[Collect]` predicate (a walk) read anything and write values at once: their own `ref`/`OptionalRef` columns, `Edit`/`Replace`/`Set` of a component present and enabled, a row overwrite of an existing key, an edge payload change. Every other write records, through any handle to the world: adds, removes, enables, disables, creates (reserved, as an observer's are), destroys, cancel-destroys, detaches, reattaches, reparents, `Batch`, row adds and removes, and edge adds, removes and retargets. Reads see recorded component changes at once through the pending overlay, a later row's value columns included, and recorded row and edge changes once the walk closes; the walk skips a later row whose recorded changes, or an ancestor's recorded destroy or detach, take it out of the query. What a walk recorded applies when the outermost walk closes, before its `RunX` returns, without delivering events or finalising; its events wait for the next playback. A walk opened inside a playback or an observer, or while an `EntityBatch` is open or serial changes already wait, leaves its records with them for the next playback; commands a parallel body recorded never hold it back, and apply after it. When a kernel-run body throws and applying what it recorded fails too, both are thrown. Playback, `Clear`, `Reset`, capture and the other settled-only calls throw inside a walk. A `[Collect]` act runs once the walk has closed, its world writes applying at once.
- A parallel body writes its own `ref` columns and reads through a `WorldReader` parameter (or `EntityReader`, the read half of `WorldEntity`), and records structural changes through its `Commands` parameter; it may take neither a `World` nor a `WorldEntity`, and a serial body no `Commands` (TECS0015). They apply at the next playback, and its reads see none of them. `Commands.Create` returns a placeholder valid only in that buffer (TECS0011).
- An observer's creates, adds, removes, enables, disables and detaches record and apply later in the same playback; outside finalisation its destroys, cancels and reparents apply at once. While a finalising playback releases its plan, destroy observers read a frozen world: every structural write they make, destroys, cancels, reparents and edge and row adds and removes included, records and applies after the release, in the same playback, while a value write applies at once, as in a walk. An observer that throws stops nothing: the playback finishes, then throws. Rescue a dying entity with `CancelDestroy` before finalisation. Its reads, like those inside an open `EntityBatch`, see a recorded add, remove, enable or disable at once through the pending overlay. An entity left with changes waiting keeps them in order: until they apply, its later structural changes record too. A recorded destroy is checked against target policies when it applies: at playback, after the batch's reparents, or at its `EntityBatch`'s dispose. One that would break a `Throw` relation is spared and reported, as is a root that finalisation finds breaking one, so a broken policy costs that root, never the world's other destroys. A recorded edge or reparent whose target is dying or gone at apply gets that target's policy, and a revival (`CancelDestroy`, or a reparent out of a dying subtree) that would leave a live `Throw` source onto a dying target is refused.
- Relation edges and rows apply at once, except inside a walk (above) and those naming an entity an observer created, which wait for it, as do later edge writes on either end of a waiting edge and later writes to an owner's rows of a type with one waiting.
- `Destroy` marks pending; the entity stays readable until a finalising playback. `StateOf` reports `PendingDestroy` for its descendants too.
- Only a `[Tracked]` component, enableable tag or rows type carries change stamps, and every stamp reader (`Changed<T>()`, `ChangedRows`, `VersionOf`, `[Changed<T>]`, a watch's `Component`/`Rows` input) requires `ITracked`, so reading an untracked type is a compile error rather than a silent zero. A `[PropagateChanges]` type gets a stamp slot either way, since propagation runs inside the stamp call. A relation, a sparse tag or a plain tag has nothing to stamp (TECS0042), and `Changed<T>` on an inherited tag is rejected (TECS0020), since an inheriting row holds no stamp of its own.
- A change sample skips what queries skip: `Changed<T>()` and `ChangedRows<TKey, TRow>()` leave out an entity (for rows, the owner) pending destroy or detached as the sample is read, unless `CursorOptions.IncludePendingDestroy`/`IncludeDetached` opt in, and `Changed<T>()` leaves out a disabled one. A sample holds stamps only: adds of untracked types, removals and disables reach a consumer through a watch.
- A consumer that turns changes into per-entity work declares a `ChangeWatch` (`Changes.Watch<TBits, TScope>`) rather than walking a sample: each input names its type, the bits it owes and its `Hop` to the entity that owes them; the watch routes value stamps, row stamps and the structural changes its inputs ask for alike, marks `TScope.Whole` for an entity back from detached, pending destroy or a restore, routing each input's `Hop` from it, and `TScope.Everything` when its queue overflowed `WorldOptions.WatchQueueCap` or the world was reset to a snapshot, and forgets destroyed entities. A `Clear` or `Reset` empties every `ChangeSet` a watch has collected into, so a mark made by hand afterwards survives the next collect. Every queued change passes one gate, the entity exists and is admitted, before the scope or a route is asked, and what they change during a collect is marked at the next. A cursor commits its sample's `Window`, so a commit across a reset or clear does nothing. Each watch owns its queue: a structural change is kept only for the watches whose inputs name its type and kind, and work that would report one nobody wants is skipped. `Presence<T>` follows adds, removes and enable flips of an untracked type. `Descendants<TOwner>` is pushed by the raise walk itself, once per owner per window, so a losing parent is queued when its version rises and a collect costs what changed, not how many owners exist; an owner pending destroy or detached waits for its resync. The ordered entry stream, with attribution, is `World.AttributedLog`, kept only when `AttributedLogCapacity` is set.
- `ChangedRows<TKey, TRow>()` is the rows counterpart of `Changed<T>()`, with the same window (after `Since`, up to `Until`): each row stamped in it with its owner and key, a row added in it included (`Added`). Removals reach a watch's `Rows` input as `RowRemoved`. A write inside `Untracked()` stamps nothing, so it is never reported, and a row it adds reaches no watch, so rows seeded inside it arrive unreported; its removes still reach watches; a recorded row write keeps the scope it was written in. It visits only owners with a row stamped after `Since`. One walk per rows type may be open at a time: a second, from any sample, throws until the first is disposed, because starting a walk reorders the chain an open one follows.

## Declarations

- `[Component]`, `[Tag]`, `[Relation]`, `[Rows]` with a `[RowKey]` field. A type's identity is its fully qualified name, which must be unique across every loaded module (TECS0002); a closed generic is declared with `[assembly: ComponentInstance<T>]`.
- Options: `[Enableable]`, `[Storage(StorageKind.Sparse)]`, `[ReplaceOnly]`, `[Singleton]`, `[Tracked]`, `[PropagateChanges(...)]`, `[UniqueIndex]`/`[MultiIndex]`/`[OrderedIndex]`, and `[Rows(PresenceMask = true, ReverseKeyIndex = true)]`.
- Relation and row types are not components: component verbs reject them at compile time.
- `CaptureImage.Write`/`Read` store values as laid out, so reading finds each type by its name or an `[Alias]` and refuses one whose `SchemaVersion` or physical layout (field types, order and offsets, never names) changed since the write, and a managed type has no byte form. Bump `SchemaVersion` when a field's meaning changes but its layout does not.
- Systems: `[System] partial class X : SystemBase` overriding `OnRun`, with `[Query]` methods called through the generated `RunX`. Nothing about a system's access is declared or inferred: a schedule never runs two systems at once, so its order is total. A schedule (`[Schedule, Set<...>]`) runs its sets in declaration order and each set's systems in the order they were added (`ScheduleBuilder.Add`, `Schedule.Add`), then the systems in no set, in the order they were added; it requires every system in its sets to be added; build it per world with `ScheduleBuilder.Build(world)`. After each system that runs, if it left recorded commands or observer events, the schedule plays back there (non-finalising, reported as `After{System}`), so the next system sees its changes; a named `[PlaybackPoint]` sits right after its `After` target or right before its `Before` target, and `Run`, `RunSet<TSet>` and `RunSystem<T>` each end with a playback; `ScheduleBuilder.Observe` takes an `IScheduleObserver` that wraps each set, system run and playback (profiler zones, tracing) and hears each skip. `ScheduleBuilder.ConfigureSet<TSet>(s => s.RunIf(...))` gates every system of a set, those added after the build too: it is checked once per run of the set (`Run`, `RunSet<TSet>`, and `RunSystem<T>` of a member) before each member's quarantine, condition and cadence; a false or throwing one (`IFaultSink.OnSetFault`) skips each member as `SystemSkip.Condition`, leaving its cadence and quarantine probe untouched, and never skips a playback point, since a point also applies and finalises what systems outside the set recorded. Bootstrap with `Registry.Build(EcsModule.All)`.

## Generated code

The generator emits into the consumer assembly; `Tralys.Ecs.Generated` holds the runtime plumbing it calls (`Plumbing`, factories, `[Effect]`). Hand-written code does not use that namespace. `tests/Tralys.Ecs.Aot.Smoke/Generated/` is checked in: its diff shows what each emitter change does to real output.
